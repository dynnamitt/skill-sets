# graph-in-pane: design

A Claude Code mod (a plugin of function hooks) that shows Graphviz graphs as
real images in a pane docked on the right of the chat in kitty. It gives
"code inspection from 10,000 feet" for scripts and builds. It also keeps a
live box-and-arrow view of a plan while one is being worked out in the chat.

Status: design approved by the owner on 2026-10-25. Implementation plan next.

## Why

The owner works in kitty with vertical splits and often wants to see how a
script flows without reading all of it. Examples: a Vite build, any bash
file, `xbox-bluetooth-linux/scripts/ble-pair.sh`. In planning chats and
design interviews, a picture of the plan as it takes shape helps more than
another wall of text. Graphviz is already installed (`dot` from Homebrew).
Some of the owner's scripts already write `.dot` files: `ble-pair.sh` draws
its own live flowchart in kitty from `ble-pair.dot` using `kitten icat`.
That script is prior art for the look and the pipeline.

**End goal (owner, 2026-10-25): fewer kitty vsplits.** Views the owner
keeps in a side split today should live in the pane instead: a flowchart, a
rendered `.dot`, or a picture of the plan. Success means the owner reaches
for a vsplit less often. A pane is not a terminal. Interactive programs
(nvim, htop, a shell) stay out of scope.

## Goals

1. **`/graph-tree <file|dir>`**: a literal structure graph. It is instant,
   deterministic and calls no model.
2. **`/graph-flow <file|dir>`**: a 10,000-foot flow graph. Claude writes it
   from a tree-sitter skeleton plus the source.
3. **Automatic plan graph.** During planning and interviews, Claude keeps a
   graph of the plan under discussion up to date in the pane.
4. **Drill-down.** Boxes that stand for the owner's own code can be opened.
   The pane navigates into them, shows a breadcrumb, and has a back button.
5. **Existing `.dot` files.** Passing a `.dot` file to either command just
   renders it. *Claude's call, serving the vsplit goal:* the pane re-renders
   when that file changes. Scripts like `ble-pair.sh` rewrite their `.dot`
   live, so the pane can follow them instead of a split running
   `kitten icat`. The engine has no file-watch API in the types, so this
   polls the file's mtime on `$.clock`. The interval is the builder's call,
   about 1 s, and polling stops when the pane closes.

## Non-goals

- Mermaid, in any form. The owner ruled it out.
- SVG. The terminal surface has no `Svg` element, and the owner uses the
  terminal.
- Graphs inline in the chat transcript. The pane is the only place they show.
- Following dependencies into `node_modules`, system tools (`bluetoothctl`,
  `dot`), or anything outside the owner's own files. These show as plain leaf
  boxes with no number.
- Languages beyond bash, TypeScript and JavaScript in the first version.
- A history of past graphs. A new graph replaces the old one. The breadcrumb
  is the only "history".
- Desktop, VS Code and mobile surfaces. Terminal (kitty) is the target. Other
  surfaces may show the `alt` text, and that is acceptable.

## Anti-goals (would make it a failure even if it "works")

- `/graph-flow` showing arrows that are not in the code. The tree-sitter
  skeleton is the evidence, and every edge Claude draws for a file must be
  traceable to it. A 10,000-foot arrow may merge several skeleton calls.
  *Claude's call:* this is enforced by instruction (the skeleton goes to
  Claude with the rule), not by a validator in the mod. Plan graphs are
  exempt, because they come from the conversation, not from code.
- `/graph-tree` spending tokens or waiting on the model.
- Keybindings that need AltGr on a Norwegian keyboard (`[]{}<>\|`). Use
  digits, letters, Backspace, arrows.
- Redrawing the plan graph every turn when nothing changed. That is noise.
- Several stacked panes for drill-down. The owner chose one pane with a
  breadcrumb.

## Portability (owner requirement)

The mod must work on **any Linux distro**. Bazzite (Fedora atomic,
Homebrew) and Arch are the current targets, not the only ones.
- **Executables (`dot`, `ast-grep`, `tree-sitter`, `nvim`).** Never hardcode
  paths. Look them up on `PATH` first, then in common user-install
  locations: `/home/linuxbrew/.linuxbrew/bin`, `~/.linuxbrew/bin`,
  `~/.cargo/bin`, `~/.local/bin`, and the npm global bin. Optional
  `userConfig` fields override each one. Do the lookup once per session and
  cache it in `$.state`.
- **Missing tools.** Report a missing tool in the pane with the install line
  for the detected distro. Read `ID`/`ID_LIKE` from `/etc/os-release`, and
  include `brew` when it is present:
  - Arch: `pacman -S graphviz ast-grep`.
  - Fedora/Bazzite: `brew install graphviz ast-grep`, or `dnf install
    graphviz` on mutable Fedora.
  - Debian/Ubuntu: `apt install graphviz`, plus `cargo install ast-grep` or
    `npm i -g @ast-grep/cli`.
  - Generic fallbacks: `cargo` and `npm`.
- **ast-grep binary name.** Always call `ast-grep`. `sg` is shadow-utils'
  `newgrp` helper on every distro.
- **Neovim parsers.** Never assume one path. Ask `nvim --headless` for
  `parser/*.so` on its runtimepath first. Then fall back to
  `${XDG_DATA_HOME:-~/.local/share}/nvim/site/parser` and
  `…/nvim/lazy/nvim-treesitter/parser`. With no parsers, ast-grep's built-in
  grammars are enough.
- **Images.** These need a terminal with the kitty graphics protocol (kitty,
  Ghostty, and others). Elsewhere the `Image` draws its `alt`, so `alt`
  carries a useful text outline of the graph (node labels in rank order),
  not just "graph".
- **Writable paths.** Temp and cache files go under
  `${XDG_CACHE_HOME:-~/.cache}/graph-in-pane/`. No `/tmp` assumptions, no
  root access, nothing that needs `sudo` or rpm-ostree.

## Constraints (verified on this machine, Claude Code 2.1.310)

- **Mod runtime.** It has no Node, no DOM, and deliberately no WebAssembly,
  so `web-tree-sitter` cannot run inside the mod. Everything external goes
  through `$.process.run(argv)`. That call has no shell, is one-shot, has a
  30 s default timeout (10 min max), and returns up to 4 MiB per stream.
- **Images in a pane.** The terminal surface has an `Image` element
  (`source: { png } | { file, format }`, `columns`, `rows`, `alt`). It draws
  with the kitty graphics protocol. `Image` is a leaf element: no `onPress`
  and no click coordinates. Drill-down therefore uses buttons and number
  keys, not clicks on the picture.
- **Pane placement.** Checked against `PaneOpenArgs` and `$.ui.open`.
  - **Asked.** An open caused by the person (a command, a prompt they
    entered, or a press) is placed at any width. In fullscreen it docks
    beside the transcript from 110 columns. Otherwise it sits inline above
    the prompt.
  - **Unasked.** An open the mod makes on its own is placed only from 144
    columns. Once the person has opened that id themselves (in this or an
    earlier session, and not closed it by hand since), the floor drops to
    110. Below the floor the pane **waits undrawn**: it does not fall back
    to inline.
  - **Plan graphs are probably unasked.** A `show_graph` call from Claude in
    the middle of a turn likely counts as unasked. The builder must test it.
    Consequences:
    - all graphs share **one pane id** (`graph`), so any `/graph-tree` or
      `/graph-flow` lowers the floor for plan graphs to 110;
    - there is a `/graph` command to (re)open the pane;
    - when a plan graph is drawn but not placed, the status line says
      `plan graph updated · /graph`.
- **Tree-sitter on the host.**
  - The `tree-sitter` CLI 0.26.11 comes with the Bazzite image, but no
    grammars are configured (`~/.config/tree-sitter` is missing).
  - `/usr/bin/sg` is shadow-utils, not ast-grep.
  - ast-grep 0.51.0 is installed at `/home/linuxbrew/.linuxbrew/bin/ast-grep`
    (`brew install ast-grep`, 2026-10-25). It bundles tree-sitter grammars
    for bash, TS and JS and outputs JSON. Always call `ast-grep`, never
    `sg`, which shadow-utils shadows on `PATH`.
  - Bash patterns like `$NAME() { $$$ }` fail to parse. Use kind rules
    instead. This one, checked on `ble-pair.sh`, returns its 19 functions:
    `ast-grep scan --inline-rules 'id: fn\nlanguage: bash\nrule: { kind: function_definition }' --json=compact <file>`
- **Neovim's prebuilt parsers.** Suggested by the owner. LazyVim, with its
  config at `~/.config/nvim` → `~/code/lazyvim-starter` and nvim-treesitter
  on the `main` branch, has 28 compiled grammars in
  `~/.local/share/nvim/site/parser/*.so`. These include bash, typescript,
  tsx, javascript, python, lua, c, java, json, yaml, toml, markdown, html,
  xml, vim and ninja. Two ways to use them, both tested:
  - The system CLI parses with them directly:
    `tree-sitter parse --lib-path …/bash.so --lang-name bash <file>`. On
    `ble-pair.sh` it finds the same 19 `function_definition`s as ast-grep.
    This is the fallback when ast-grep is missing.
  - ast-grep loads them as `customLanguages` in an `sgconfig.yml`, with
    `libraryPath` pointing at the `.so`. This only works with
    `--custom-languages allow`, because ast-grep gates native libraries for
    security. Tested with `ninja.so`.

  Language discovery order: ast-grep's built-in grammars first, which
  already cover bash, TS/JS, Python, Lua, C, Java and more. Then nvim's
  `.so` files for anything ast-grep lacks. The parser directory is found via
  `nvim --headless` (`vim.api.nvim_get_runtime_file('parser/*.so', true)`)
  or by falling back to the path above. Discovery makes adding a language
  cheap. Flow rules still ship only for bash and TS/JS in v1.
- **`ast-grep outline`** (symbols, imports, exports) reports "nothing found"
  for bash. It may still be useful for TS/JS. The builder should check.
- **Graphviz.** `dot` lives at `/home/linuxbrew/.linuxbrew/bin/dot`. Do not
  assume it is on the mod process's `PATH`. Resolve it once at
  `session.start`, for example with `$.process.run(['sh','-c','command -v dot'])`
  or a `userConfig` path, and report clearly if it is missing.
- **Repo conventions.** This lives in `dynnamitt/skill-sets`, a public repo.
  Commit each verified change on its own. The owner pushes. Code style is
  functional (`map`/`filter`/`reduce`, no mutation-heavy loops), and that
  applies to the mod's TS as well.

## Decisions made with the owner

| Topic | Decision |
|---|---|
| Rendering | Graphviz `dot -Tpng` shown as an `Image` in a pane. No Mermaid. |
| Commands | Two commands: `/graph-tree` (literal) and `/graph-flow` (10,000 ft). Both take `<file\|dir>`. |
| Parser | Tree-sitter, run as an external helper. |
| Layout | Top-down (`rankdir=TB`). Pane docked on the right. |
| Drill-down | Own files only. One pane, breadcrumb, back button. |
| Auto trigger | The plan under discussion, drawn as boxes and arrows, during planning and interviews. |
| Home | `~/code/skill-sets/graph-in-pane/`. |

The browser mockups were approved as "looks fine". They showed three
moments:
- **A.** The plan pane during a chat.
- **B.** `/graph-flow ble-pair.sh` with yellow numbered boxes and a key row
  `1: choose adapter  2: pick gamepad`.
- **C.** After pressing 2: `← back (0)  ble-pair.sh › pick gamepad`.

## Claude's calls (not explicitly confirmed; reasonable to keep)

- **Command names.** `/graph-tree` and `/graph-flow`.
- **Aliases (owner, 2026-10-25).** `/10kfo` (o = overview) runs
  `/graph-flow`. `/10kfv` (v = view) runs `/graph-tree`; the mapping of `v`
  to the literal view is Claude's reading. The engine has no alias field,
  so each alias is a second `$.command.register` answered by the same
  handler.
- **Dark theme.** Catppuccin-like colours. Every graph gets them from one
  shared style preamble, so plan graphs, tree graphs and flow graphs look
  alike.
- **Box colours.**
  - Openable boxes are yellow-bordered and carry a circled digit (①–⑨).
  - Exits are ovals: green for success, red for failure.
  - External tools are grey cylinders.
- **Navigation keys.** The owner decided on 2026-10-25 that the key row
  stays **inside the pane**.
  - Digits 1–9 open a numbered box, as buttons (`<Button hotkey="1" plain>`).
  - `0` goes back. Backspace cannot be a hotkey: only one digit or one
    lowercase letter is allowed.
  - Hotkeys fire only while the pane has focus: after ctrl+x tab or a click.
    No band above the prompt.
  - The mod never opens the pane with `focus: true`, so typing stays in the
    chat. The pane's key row shows a dim `ctrl+x tab to use keys` hint while
    the pane is unfocused (`isFocused` on the Pane props).
  - More than 9 openable boxes is left to the builder (see below).
- **One pane id, `graph`**, for every graph. Plus a `/graph` command to
  reopen it and `/graph off` to end a planning context (see Constraints:
  pane placement).
- **When a planning context ends.**
  - It ends on `ExitPlanMode`, on leaving plan mode, on `/clear`
    (`session.end` with `reason: 'clear'`), or on `/graph off`.
  - A planning context started by the brainstorming or writing-plans skill
    lasts until one of those, or the end of the session.
  - Plan mode entered with shift+tab counts too. Detect it from the
    permission mode on turn events, not only the `EnterPlanMode` tool call.
- **Drill-down inside one file.** When a file has no own-file dependencies,
  large functions in it count as openable boxes. Example: `ble-pair.sh`
  sources nothing, but `gamepads()` and `pick()` can be opened.
- **Drill-down mode.** It keeps the mode it started in. From `/graph-tree`
  it opens literally. From `/graph-flow` it asks Claude for the next level.
- **`/graph-flow` runs in the main chat**, not in a hidden subagent, so the
  owner can ask follow-ups straight away.
- **A `show_graph` tool for Claude.** The mod registers it with
  `$.tool.register`. Input: `{ title, dot, openable?: [{ n, label, target }] }`.
  It is the single path Claude uses to put any graph in the pane: plan
  graphs, `/graph-flow` results, and drill-down levels.
- **Plan triggers.** (When they end: see "When a planning context ends"
  above.) A short instruction section is added via
  `prompt.compose` with `scope: 'session'`. It is switched on when a
  planning context starts and tells Claude to keep the plan graph current.
  Planning contexts:
  - the `superpowers:brainstorming` or `superpowers:writing-plans` skill
    loads (`skill.prompt` event);
  - plan mode starts (`EnterPlanMode` tool call).

  Outside those contexts, `show_graph` stays available but Claude is not
  prompted to use it.
- **Redraw rule.** Claude calls `show_graph` for the plan only when nodes or
  edges change.
- **Graph size.**
  - Render at a DPI that suits the pane's `bodyColumns` × rows, and size the
    `Image` to fill the pane body.
  - Re-render on width change; the engine re-runs `ui.render` on resize.
  - Dir graphs and very large files may collapse to a summary (for example,
    one box per file) rather than an unreadable picture.

## How it works (the agreed shape; details are the builder's)

```
/graph-tree X ─┐                           ┌─► .dot file? render as-is
               ├─► extract (ast-grep JSON) ─┤
/graph-flow X ─┘        │                  └─► skeleton
                        │
   graph-tree: skeleton ─► DOT (deterministic, in the mod)
   graph-flow: skeleton + source ─► Claude ─► show_graph(dot, openable)
   plan:       conversation ─► Claude ─► show_graph(dot)
                        │
                 dot -Tpng (TB, shared style) ─► PNG file
                        │
                 Pane: title · breadcrumb/back · Image · key row 1–9
```

**Skeleton.** It is extracted per file with ast-grep rules for each
language, then merged for a directory.
- Bash: functions, calls to functions, `exit`/`return` with codes,
  `if`/`case`/loop structure at the top level, external commands, and
  `source`/`.` of own files.
- TS/JS: functions and exported symbols, calls, `import`s (relative ones are
  own files), and the plugins array for Vite configs.

"Own file" means the path resolves inside the target's directory tree or the
git repository it belongs to, and outside `node_modules`.

**State.** The breadcrumb stack, the current graph (title, PNG path, the list
of openable boxes) and the mode go in `$.state` atoms, declared in
`types/index.d.ts`. They survive hot reloads. PNGs are written under a temp
or cache directory owned by the mod.

**Errors appear in the pane as text, never as a blank pane.** Cases:
- unsupported language: "no grammar for X";
- `dot` or `ast-grep` missing, with the install line (`brew install ast-grep`);
- a DOT syntax error, with the first stderr line;
- a file not found.

## Left to the builder

- The exact ast-grep rules and the JSON-to-skeleton mapping.
- How `/graph-flow` hands the work to Claude, and how a drill-down from a
  `/graph-flow` graph asks for the next level. Candidates:
  - `$.prompt.submit`, which the reviewer found in the types;
  - `command.run` returning `context` as a hidden note to the model;
  - a `prompt.submit` rewrite.

  Verify which one actually starts a model turn on this build. The chosen
  path must end in a `show_graph` call.
- What happens with more than 9 openable boxes: paging, or the key row
  listing only the first 9 with a "more" button.
- PNG cache location and cleanup.
- Whether DOT is generated by string templates or a tiny pure builder. It
  must be pure functions in either case.
- Test coverage (`claude plugin test`). At minimum, cover:
  - skeleton → DOT for a fixture bash file;
  - the breadcrumb push/pop reducer;
  - the error paths.
- The marketplace entry, a root `.claude-plugin/marketplace.json` listing
  `./graph-in-pane`. Also a README row in skill-sets, and an update to
  skill-sets' `CLAUDE.md`. Today it says the repo is "pure markdown, no
  source code", so it needs to describe the new plugin folder kind. Every
  `.md` in the repo carries `name`/`description` frontmatter. Publishing follows the
  plugin-authoring "Sharing a mod" steps when the owner asks.
- How to develop it. One option is `claude --plugin-dir
  ~/code/skill-sets/graph-in-pane`, which hot-reloads. Another is writing in
  the session's dev-mods folder and then moving the files. Do not end up
  with two diverging copies; symlink if needed.
